# 功能规划 SKILL

> **用途**：记录、评估和规划功能需求
> **触发方式**：`/feature [需求描述]`

---

## 执行流程

### 1. 获取需求

从参数中获取用户的需求描述。如果没有参数，提示用户提供需求。

### 2. 查看相关文档

根据需求类型，读取相关文档：

| 需求类型 | 需要查看的文档 |
|---------|---------------|
| 新功能 | `docs/requirements.md`, `docs/architecture.md` |
| UI/交互 | `docs/design.md`, `docs/requirements.md` |
| 数据相关 | `docs/database.md`, `docs/architecture.md` |
| 性能优化 | `docs/architecture.md`, `docs/database.md` |
| 国际化 | `CLAUDE.md`（国际化原则） |

同时查看：
- `docs/todolist.md` - 当前进度和计划
- `docs/progress/` - 已完成的工作

### 3. 需求分析

#### 3.1 合理性评估

评估需求是否合理：
- 是否符合项目定位（健康管理应用）
- 是否与现有功能冲突
- 实现成本是否合理
- 是否有替代方案

#### 3.2 架构影响评估

评估对现有架构的影响：
- 是否需要新增数据库表
- 是否需要修改现有数据结构
- 是否需要新增服务层
- 是否需要修改导航结构
- 是否影响现有功能

#### 3.3 技术可行性

评估技术实现的可行性：
- 是否有现成的库/工具支持
- 是否需要原生模块
- 跨平台兼容性
- 性能影响

### 4. 设计方案

如果需求合理，制定设计方案：

#### 4.1 功能设计
- 功能描述
- 用户交互流程
- 界面设计（参考 `docs/design.md`）

#### 4.2 技术设计
- 数据模型变更（如有）
- API 设计（如有）
- 组件设计
- 状态管理

#### 4.3 实现步骤
- 分解为可执行的任务
- 确定任务优先级
- 估算工作量

### 5. 安排 TODOLIST

将需求安排到 TODOLIST：

#### 5.1 新增 Phase（如果是大型功能）

```markdown
## Phase X：功能名称

> **目标**：功能描述
> **预计时间**：X 天

### X.1 子任务 1
- ⬜ 任务 1
- ⬜ 任务 2

### X.2 子任务 2
- ⬜ 任务 3
- ⬜ 任务 4
```

#### 5.2 添加到现有 Phase（如果是小型优化）

在现有 Phase 中添加任务项。

#### 5.3 更新进度跟踪表

更新 `docs/todolist.md` 中的进度跟踪表。

### 6. 记录需求文档

创建需求文档：`docs/features/feature-name.md`

```markdown
# 功能名称

## 需求描述
用户的需求描述

## 合理性评估
- 评估结论
- 优缺点分析

## 架构影响
- 数据模型变更
- 组件变更
- 服务变更

## 设计方案
### 功能设计
- 功能描述
- 交互流程

### 技术设计
- 数据模型
- 组件设计
- API 设计

### 实现步骤
1. 步骤 1
2. 步骤 2

## 工作量估算
- 预计时间：X 天
- 复杂度：高/中/低

## TODOLIST 安排
- Phase X, 任务 X.X
```

### 7. 告知用户

向用户报告：

```
## 📋 需求评估报告

**需求**：[需求描述]

### 合理性评估
- ✅ 合理 / ⚠️ 需要讨论 / ❌ 不合理
- 原因：...

### 架构影响
- 数据模型：无变更 / 需要新增表 / 需要修改表
- 组件：无变更 / 需要新增组件 / 需要修改组件
- 服务：无变更 / 需要新增服务 / 需要修改服务

### 设计方案
- 功能描述：...
- 交互流程：...
- 技术实现：...

### TODOLIST 安排
- Phase X, 任务 X.X
- 预计时间：X 天

### 下一步
- 确认需求，开始开发
- 或调整需求方案
```

---

## 需求分类

### 新功能
- 全新的功能模块
- 需要新增 Phase
- 需要完整的设计文档

### 功能增强
- 现有功能的改进
- 添加到现有 Phase
- 更新相关文档

### 优化改进
- 性能优化
- 代码重构
- UI/UX 改进
- 可以安排到现有任务

### Bug 修复
- 问题描述
- 影响范围
- 修复方案

## 示例

### 示例 1：新功能需求

```
/feature 添加饮水记录功能
```

**输出**：
```
## 📋 需求评估报告

**需求**：添加饮水记录功能

### 合理性评估
- ✅ 合理
- 健康管理应用应该包含饮水记录
- 与现有饮食记录功能互补

### 架构影响
- 数据模型：需要新增 `water_records` 表
- 组件：需要新增饮水记录组件
- 服务：需要新增饮水记录查询

### 设计方案
- 功能：记录每日饮水量，设置目标，提醒饮水
- 交互：快速记录按钮，进度展示
- 数据：时间戳、饮水量（ml）

### TODOLIST 安排
- 新增 Phase 7：饮水记录功能
- 预计时间：3 天

### 下一步
- 确认需求，开始开发
```

### 示例 2：优化需求

```
/feature 优化首页加载速度
```

**输出**：
```
## 📋 需求评估报告

**需求**：优化首页加载速度

### 合理性评估
- ✅ 合理
- 性能优化是持续改进的一部分

### 架构影响
- 数据模型：无变更
- 组件：可能需要优化数据加载逻辑
- 服务：可能需要添加缓存

### 设计方案
- 问题：首页加载时查询多个表，响应慢
- 方案：
  1. 添加数据缓存
  2. 优化查询语句
  3. 使用懒加载

### TODOLIST 安排
- 添加到 Phase 4（基础 UI 组件）的优化任务
- 预计时间：1 天

### 下一步
- 确认需求，开始优化
```

---

## 注意事项

1. **需求合理性**：不是所有需求都应该实现，要评估 ROI
2. **架构影响**：大型变更需要谨慎，避免破坏现有功能
3. **工作量估算**：给出合理的时间估算，避免过度承诺
4. **优先级排序**：根据重要性和紧急性安排优先级
5. **文档同步**：需求变更时及时更新相关文档
